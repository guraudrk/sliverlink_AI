### 구현 및 변경 내용

**auth.uid() 원인 규명 (SQL·코드 수정 없음, 분석만)**

핵심 추론 경로:
1. `run_demo_seed` 함수는 `GRANT EXECUTE TO authenticated` — anon 역할로 호출하면 "permission denied"로 즉시 실패한다
2. 데모 seed가 실제로 실행됐다 = authenticated JWT가 전달됐다 = auth.uid()는 NULL이 아니다
3. 실제 실패 지점은 `organizations` 테이블: SELECT·UPDATE 정책만 있고 INSERT 정책이 없다
4. INSERT 정책 없음 → org 생성 실패 → `org_members` 편입 안 됨 → `is_org_member()` false → `parent_profiles` INSERT 실패
5. 결론: SECURITY DEFINER `run_demo_seed`로 처리하는 현재 구조가 올바르다. auth.uid() NULL 가설은 틀렸다.

**run_demo_seed 보안 강화 (Supabase SQL Editor에서 직접 적용)**

추가한 보안 검사 (함수 진입부):
```sql
IF auth.uid() IS DISTINCT FROM p_user_id THEN
  RAISE EXCEPTION 'run_demo_seed: forbidden (caller=%, requested=%)',
    auth.uid(), p_user_id;
END IF;
```
- `IS DISTINCT FROM` 사용 이유: NULL-safe 비교. auth.uid()가 NULL이면 (anon 호출) 역시 예외 발생
- REVOKE EXECUTE FROM PUBLIC; REVOKE FROM anon; GRANT TO authenticated 재정비
- 부수 효과: 이 검사가 통과했다 = auth.uid() = p_user_id = NULL이 아님 — 진단 도구로도 기능

### 문제와 해결 과정

**막혔던 지점: "auth.uid()가 NULL"이라는 잘못된 가설**

이전 세션에서 `parent_profiles` INSERT 실패를 auth.uid() NULL로 오진단했다. 오늘 재조사에서 SECURITY DEFINER 함수의 권한 모델을 역추론해 실제 원인(organizations INSERT 정책 부재)을 밝혔다. 교훈: RLS 오류 메시지는 원인이 아니라 결과를 보고한다. 체인의 첫 번째 실패 지점을 찾아야 한다.

**선택: NULL-safe 비교 연산자**

`auth.uid() != p_user_id` 대신 `auth.uid() IS DISTINCT FROM p_user_id` 사용.
PostgreSQL에서 `NULL != X`는 TRUE가 아니라 NULL을 반환한다. anon 호출(auth.uid() = NULL)을 막으려면 NULL-safe 비교가 필수였다.

### 요청과 목표

### 구현 및 변경 내용

**S1 — paste_text 생성 로직**

기존 `generateBatchReportText`는 AI가 생성한 텍스트 1개만 반환했다.
이번에 AI가 5섹션 보고서(`summary_md`)와 복붙용 4줄(`paste_text`)를 같은 호출에서 동시에 생성하도록 구조 변경.

분리 방식: 프롬프트 끝에 `---PASTE---` 구분자 지시 추가. AI가 5섹션 작성 후 구분자를 출력하고 바로 아래에 복붙용 4줄을 쓰도록 `BATCH_SYSTEM_PROMPT`에도 규칙 추가.

```
---PASTE---
[기간] 이름 어르신
· 통화 N회 중 M회 응답 (응답률 X%)
· 특이사항: (AI 생성)
· 상태: (AI 생성)
· 권장: (AI 생성)
```

파싱: `splitReportOutput(raw, data, facts)` — `---PASTE---` 인덱스로 분리.

### 문제와 해결 과정

**paste_text 생성 방식 선택**

옵션 A (AI가 `---PASTE---` 구분자로 두 형식 동시 출력) vs
옵션 B (AI 없이 수치만으로 코드 조합) vs
옵션 C (AI에게 JSON 구조화 출력 요청)

선택: A 방식.
- B: 특이사항·권장 조치는 수치만으로 생성 불가 → 결국 AI 필요
- C: JSON 파싱 실패 위험 + 긴 텍스트를 JSON 값으로 이스케이프하는 것이 불안정
- A: 이미 AI가 두 섹션의 컨텍스트를 알고 있으므로 paste 생성 품질이 높음. 파싱 실패 시 fallback으로 수치만 사용하면 됨.

**CSV `parent_profiles` 조인 타입 에러**

Supabase `.select("..., parent_profiles(display_name)")` 조인 시 TypeScript 추론 타입이 `{ display_name: any }[]` (배열). 정의한 `ReportRow.parent_profiles`가 `{ display_name: string } | null` (단일)이라 불일치.
해결: `.map()` 에서 `Array.isArray` 체크 후 `[0]` 추출로 정규화.

### 기술적 의사결정

| 결정 | 이유 |
|------|------|
| 기관 커스텀 템플릿에서 수치 변수는 JS에서 치환, AI 생성 변수는 AI 지시로 채움 | 수치(통화 횟수·응답률 등)를 AI에게 맡기면 환각 위험. 이미 `computeReportFacts`로 계산된 값을 JS에서 직접 주입 |

### 문제와 해결 과정

**report_send_logs INSERT RLS 문제 (미해결, 다음 확인 필요)**

`report_send_logs` INSERT 정책이 `auth.uid()` 기반 admin 체크로 설정됐다.
하지만 cron route(`/api/cron/weekly-reports`)는 `createSupabaseServerClient()`(anon key)로 실행되므로 INSERT가 RLS에 막힐 수 있다.
해결 방향 3가지:
1. service role key 사용 — 보안 정책 위반이므로 불가
2. INSERT 정책을 `WITH CHECK (true)` 또는 `auth.uid() IS NOT NULL`로 완화
3. `SECURITY DEFINER` INSERT 함수 사용

Supabase SQL Editor에서 `report_schedules.sql` 실행 후 실제 cron 호출 시 에러가 발생하면 옵션 2로 수정 필요. 현재는 `ENABLE_REAL_EMAIL=false`이므로 발송까지 도달하지 않아 문제가 표면화되지 않음.

### 문제와 해결 과정

**access_logs INSERT RLS 문제 (S3)**

cron route와 동일 문제: `access_logs` INSERT 정책을 admin 체크로 설정하면 cron에서 INSERT 불가.
S3 접근 로그는 cron이 아닌 사용자 세션에서 기록되므로 `auth.uid()`가 항상 있다 → admin 정책으로 충분하지 않음 (복지사도 보고서 조회 가능).
해결: `access_logs` INSERT 정책을 `WITH CHECK (true)`로 설정하되 SELECT는 admin만 — 누구든 INSERT하고 admin만 조회하는 구조.

현재 migration SQL에는 INSERT 정책을 아직 분리하지 않았다 — 다음 세션에서 수정 필요.

### 기술적 의사결정

| 결정 | 이유 |
|------|------|
| 접근 로그를 모든 API가 아닌 보고서 조회·CSV·삭제 3곳에만 | PRD "누가 언제 어떤 어르신 데이터를 봤는가"의 핵심 지점만 커버. 모든 API에 달면 DB write overhead + 코드 산재 |
| 파기 로직을 analyze route에 직접 삽입 (별도 함수 분리 안 함) | 분석 후 파기가 원자적으로 연결되어야 함. 실패해도 이미 분석 결과는 저장됨 |
| consent_given_at/method 컬럼 추가만 (UI 없음) | 동의 입력 UI는 어르신 관리 화면에 연결해야 하는데 Day 41 범위. 컬럼만 준비해두면 충분 |

### 구현 및 변경 내용

**S3 — 멤버 초대 플로우**

`docs/migration-v2-invite.sql`:
- `org_invites` 테이블: `token text UNIQUE DEFAULT encode(gen_random_bytes(32), 'hex')`, `role`, `invited_email`, `expires_at (7일)`, `used_at`
- RLS 3정책: admin SELECT/INSERT, 로그인 사용자 token 조회

`src/app/api/org/invite/route.ts` (`POST`):
- admin 확인 → 기존 유효 초대 있으면 재사용
- 신규 토큰 생성 → `/join?token=...` 링크 반환
- `ENABLE_REAL_EMAIL=true`이면 Resend로 초대 이메일도 발송 (선택)

`src/app/api/org/join/route.ts` (`POST`):
- 토큰 유효성 3가지 체크: 미사용(`used_at IS NULL`), 미만료(`expires_at > now()`), 존재 여부
- 401이면 `/login?next=/join?token=...` 리다이렉트 (join 페이지에서 처리)
- `org_members` upsert (이미 멤버면 role만 업데이트)
- `used_at` 소비

`src/app/(protected)/join/page.tsx` (클라이언트 컴포넌트):
- URL에서 token 파라미터 추출 → `/api/org/join` POST
- 상태: processing / success (2초 후 대시보드 이동) / error (에러 메시지 + 대시보드 버튼)
- 401 → `/login?next=...` 리다이렉트

`src/components/app/invite-member-form.tsx` (클라이언트 컴포넌트):
- 이메일 + 역할(사회복지사/생활지원사/관리자) 입력
- 초대 링크 생성 후 인라인 표시 + [복사] 버튼

`src/app/(protected)/dashboard/settings/page.tsx`:
- "멤버 초대" 섹션 추가 (admin 전용)

### 기술적 의사결정

| 결정 | 이유 |
|---|---|
| Supabase auth.admin.inviteUserByEmail() 사용 안 함 | service role key 필요 → 보안 정책 위반 |
| 자체 토큰 방식 (crypto random 32바이트 hex) | 예측 불가 토큰, 7일 만료, 1회 사용 → 충분한 보안 |
| 이메일 발송을 옵트인으로 | ENABLE_REAL_EMAIL=false인 개발 환경에서도 링크 복사 방식으로 테스트 가능 |
| token 중복 방지: 기존 유효 초대 있으면 재사용 | 같은 이메일에 반복 초대 시 토큰 누적 방지 |
