### 구현 및 변경 내용

**H1 — 권한 우회 버그 (높음)**
- `src/app/api/reports/batch/route.ts`: `reportSetId` 재개 경로에서 `org_members` 소속 확인이 누락되어 있었음. `!sample` 체크 직후 `org_members` 조회를 삽입해 미소속 사용자는 403 반환.
- 근본 원인: 신규 배치 분기에는 소속 확인이 있었지만, 재개 분기에는 없었음. `report_set_id`만 알면 타 기관 보고서에 접근 가능한 구멍이었다.

**H2 — 이메일 환경변수 누락 (높음)**
- `.env.example`: `ENABLE_REAL_EMAIL=false`, `RESEND_API_KEY=`, `EMAIL_FROM=` 추가. 이 값들은 코드에 이미 참조되고 있었지만 예시 파일에 없어 설정 방법을 알 수 없었음.
- `TEST_EMAIL=`, `TEST_PASSWORD=` 도 함께 추가 (M7).

**M1 — API 평문 에러 응답 JSON으로 통일 (중간)**
- 8개 라우트 파일에서 `new NextResponse("string", { status: N })` 패턴을 `NextResponse.json({ error: "string" }, { status: N })`으로 전환.
- 대상 파일: `org/invite`, `org/delete-elder`, `org/join`, `org/schedule`, `org/send-logs`, `org/send-logs/retry`, `org/privacy-settings`, `reports/csv`
- 이전 방식은 `Content-Type: text/plain`으로 반환되어 클라이언트 `res.json()` 파싱 시 오류 가능.

**M2 — analyze 라우트 한국어 에러 코드 → 영문 코드 (중간)**
- `recordings/analyze/route.ts`: `"인증이 필요합니다."` → `"unauthenticated"`, `"recording_id가 필요합니다."` → `"recording_id_required"` 등 5개 에러 메시지를 영문 코드로 변경.

**M3 — AI 비서 페이지 fetch 에러 처리 (중간)**

**M4 — 어르신 삭제 에러 처리 (중간)**

**M5 — `as any` 제거 (중간)**
- `recordings/analyze/route.ts`: `SupabaseClient` 타입을 임포트해 `let supabase: SupabaseClient`로 선언, `createClient()` 직접 반환값 사용. `createSupabaseServerClient()`는 `as unknown as SupabaseClient`로 축소 캐스트. `as any`보다 명시적이며 타입 추론 보존.

**M6 — ParentProfile 타입 `org_id` 누락 (중간)**

### 문제와 해결 과정

- `recordings/analyze/route.ts`의 `as any` 제거 시, `createSupabaseServerClient()`의 반환 타입이 더 특수화되어 `SupabaseClient`에 직접 할당이 안 됨 → `as unknown as SupabaseClient`로 안전하게 축소 캐스트. 완전한 해결책은 `createSupabaseServerClient`의 반환 타입을 `SupabaseClient`로 선언하는 것이지만 그 파일 범위 밖이므로 최소 변경 원칙 준수.

### 기술적 의사결정

- **B안 선택 이유**: 높음(2)+중간(7) 모두 수정. 낮음 4건도 함께 처리해 한 커밋에 깔끔히 정리. 기관 계약 전에 API 보안 결함이 남아있으면 계약이 성사되더라도 신뢰 손상 리스크.
- **평문 응답 → JSON 통일**: 모바일 앱 클라이언트가 `res.json()`으로 에러를 파싱하므로 일관성 필수. 기존 에러 문자열 값은 유지해 소비 측 코드 변경 최소화.

### 구현 및 변경 내용

**역할 분기 라우팅 (`dashboard/page.tsx`)**
- 개인 대시보드 서버 컴포넌트 최상단에 `org_members` 조회 추가
- 조회 결과가 있으면(= 기관 소속) 즉시 `/dashboard/caseworker`로 `redirect()`
- 개인 사용자에게는 기존 화면이 그대로 표시됨 — 변경 없음
- 로그인 폼은 그대로 `/dashboard`로 보내고, `dashboard/page.tsx`에서 갈림길을 처리하는 구조

**기관 대시보드에 "개인 대시보드" 진입 링크 추가 (`caseworker/page.tsx`)**
- 헤더 flex 행 오른쪽 끝에 `개인 대시보드 →` 링크 추가
- 기관 소속 사용자가 개인 기능에 접근하고 싶을 때 누를 수 있는 탈출구 역할
- 작은 `text-slate-400` 텍스트 링크로 UI를 어지럽히지 않으면서도 접근 가능

### 문제와 해결 과정

- 랜딩 페이지가 "로그인 리다이렉트 상태"라는 CLAUDE.md 메모가 있었지만, 실제로는 `landing-client.tsx`가 완전히 구현된 상태였음 — 수정 불필요
- 로그인 폼에서 역할 분기를 하는 대신 `/dashboard`에서 처리하도록 결정: 로그인 폼을 건드리지 않아도 되고, SSO·소셜 로그인 등 미래 진입 경로도 동일하게 커버됨

### 기술적 의사결정

- **분기 위치 선택**: 로그인 폼 vs. `/dashboard` 서버 컴포넌트 두 가지 선택지 중 후자를 선택. 이유: 로그인 폼 외 진입 경로(Magic Link, OAuth 등)도 `/dashboard`를 거치므로 단일 지점에서 처리하는 편이 일관성이 높다. `redirect()`는 서버 컴포넌트에서 클라이언트에 HTTP 307을 보내므로 성능 손실 없음.
- **`maybeSingle()` 사용**: `org_members`에 여러 행이 있을 수 있지만 `.limit(1).maybeSingle()`로 첫 번째 행만 확인. 소속 여부 판단이 목적이므로 행 전체 조회 불필요.
