## 세션: Day 34 S3~S7 — 기관 테넌시 마이그레이션 DB 적용 + 침투 테스트

### 요청과 목표

- S2에서 승인된 마이그레이션 SQL을 Supabase DB에 실제 적용
- 적용 후 즉시 침투 테스트(PT-0~3)로 RLS 보안 검증

### 구현 및 변경 내용

**마이그레이션 내용 (docs/migration-v2-org-tenancy.sql):**

- `organizations` 테이블 신규 생성 (id, name, slug, is_demo)
- `org_members` 테이블 신규 생성 (org_id, user_id, role: admin/social_worker/field_worker)
- `parent_profiles`에 `org_id`, `assigned_user_id` 컬럼 추가
- SECURITY DEFINER 함수 4개: `is_org_member`, `is_org_admin`, `can_access_parent`, `can_access_parent_any`
- `prevent_parent_org_change` BEFORE UPDATE 트리거: org_id·owner_user_id 클라이언트 변경 차단
- 전 테이블(14개) RLS를 `owner_user_id = auth.uid() OR can_access_parent(parent_id)` 패턴으로 확장
- `social_scores` unique 제약을 `(owner_user_id, parent_id, week_start)` → `(parent_id, week_start)`으로 변경
- `create_org_with_admin` 함수: 신규 기관 생성 + 첫 admin 원자적 등록 (anon/authenticated REVOKE)

**침투 테스트 결과:**
- PT-0: anon이 organizations SELECT → 0건 ✅
- PT-1: A기관 admin이 B기관 org_members INSERT → RLS 차단 ✅
- PT-2: 기관 멤버가 parent_profiles.org_id = NULL 로 UPDATE → 트리거 차단 ✅
- PT-3: field_worker가 비배정 어르신 SELECT → 0건 ✅

### 문제와 해결 과정

**1차 실패: 42P01 — org_members 테이블 없음**

`LANGUAGE sql` 함수는 생성 시점에 참조 테이블이 존재해야 한다. `is_org_member`/`is_org_admin`이 `org_members`를 참조하는데 테이블이 함수보다 나중에 생성돼 실패.

→ 테이블 생성을 함수 생성 앞으로 이동.

**2차 실패: 42703 — parent_profiles.org_id 컬럼 없음**

`can_access_parent`가 `pp.org_id`를 참조하는데, `parent_profiles`에 컬럼 추가는 더 나중 단계였다.

`LANGUAGE sql`은 컬럼 존재도 함수 생성 시점에 검증한다는 사실을 이 과정에서 확인.

→ 함수를 두 단계로 분리. 3A: `is_org_member`/`is_org_admin` (org_members만 참조), 3B: `can_access_parent`/`can_access_parent_any` (parent_profiles 컬럼 추가 이후).

**3차 실패: 2BP01 — ROLLBACK SQL이 자동 실행됨**

SQL 파일에 Forward 마이그레이션과 ROLLBACK SQL을 같은 파일에 넣었더니 Supabase SQL Editor가 두 BEGIN...COMMIT 블록 모두 실행했다. Forward는 성공했으나 ROLLBACK 블록이 `can_access_parent_any` DROP 시도 중 의존 정책 때문에 실패.

→ Forward 마이그레이션은 이미 COMMIT 완료 상태임을 확인. ROLLBACK 섹션을 주석 처리해 재실행 방지.

**침투 테스트 환경 구성 시행착오:**

- `SET LOCAL "request.jwt.claims" = json_build_object(...)`: 문법 오류 → `set_config()` 함수로 교체
- `SET LOCAL ROLE authenticated` 후 `auth.users` 조회: permission denied → UUID를 service_role 단계에서 미리 조회, PL/pgSQL 변수로 넘기는 방식으로 해결

### 기술적 의사결정

- **함수 분리(3A/3B)**: `LANGUAGE sql` vs `LANGUAGE plpgsql`의 검증 시점 차이를 활용. `plpgsql`로 바꾸면 런타임 오류가 되므로, 의존 순서를 올바르게 지키는 `LANGUAGE sql` 방식을 유지.
- **ROLLBACK 섹션 분리**: 같은 파일에 두 트랜잭션 블록을 넣으면 자동 실행되는 문제 → 주석으로 격리. 다음부터는 ROLLBACK을 별도 파일로 관리.
- **침투 테스트 DO 블록**: `BEGIN...EXCEPTION` 패턴으로 PASS/FAIL을 SQL 내부에서 자동 판정. 예상 실패를 에러 없이 검증 가능.

### 테스트 및 검증

- Supabase SQL Editor에서 확인 쿼리 실행: 함수 4개·테이블 2개·컬럼 2개 모두 존재 확인
- 침투 테스트 PT-0~3: 전부 통과

- `docs/migration-v2-org-tenancy.sql`: V2 기관 테넌시 마이그레이션 SQL (신규)

### 미해결 사항 및 다음 작업

- **Day 35 / S0**: 디자인 락 — `docs/design-system.md` 생성 (기관 대시보드 신규 화면 설계 전 필수)

### 문제와 해결 과정

특별한 오류 없음. S1에서 RLS가 DB 단에서 처리한다는 이전 세션의 설계 결정 덕분에 쿼리 로직 변경이 최소화됐다.

타임존 처리: `Date.now() + 9h` → UTC 기준 KST 현재 시각을 구한 뒤 요일 계산 → 월요일 자정 KST → 다시 9시간을 빼서 UTC ISO 문자열로 변환. 서버 타임존이 UTC일 경우에도 올바르게 이번 주 기준이 계산된다.

### 기술적 의사결정

- **B안 채택 이유**: A안(이번 주 통화 시도 0건)은 "아직 전화를 안 건" 어르신과 "전화를 걸었는데 안 받은" 어르신을 구분하지 못한다. 복지사가 실제로 전화를 시도했지만 연락이 닿지 않는 상황이 확인의 우선순위가 더 높다.
- **`thisWeekCallStatuses`를 DB에서 계산하지 않고 JS에서 필터**: 기존 14일 쿼리를 재사용하면 DB 왕복이 추가되지 않는다. 14일 > 7일이므로 이번 주 데이터는 항상 포함돼 있다.
- **미확인 알림은 KPI에서 제거, 개별 카드에는 유지**: `unackedAlertCount`는 여전히 `ElderSummary`에 있고, 카드 레벨 플래그(`unacked_alerts`)로 표시된다. KPI 타일이 4개로 제한되는 상황에서 복지사에게 더 능동적 행동이 필요한 "미통화" 항목을 우선했다.

## 세션: Day 35 S5 — 쿼리 구조 분석 + 성능 인덱스 마이그레이션

### 요청과 목표

- 실제 60명 데이터 없이도 할 수 있는 방식: `listElderSummaries` 4개 쿼리 구조 분석 + 누락 인덱스 파악 + SQL 작성
- 인덱스가 없으면 데이터 누적 시 어느 지점에서 느려지는지 예측

### 구현 및 변경 내용

**쿼리 구조 분석**

`listElderSummaries`는 4개 쿼리를 `Promise.all`로 병렬 실행한다:

| 쿼리 | 필터 조건 | 정렬 | 예상 데이터 규모 |
|------|-----------|------|-----------------|
| `parent_profiles` | (RLS) | `created_at DESC` | 60행 — 문제없음 |
| `social_scores` | `parent_id IN (60)` | `week_start DESC` | 60 × 26주 = 1,560행/6개월 |
| `care_call_attempts` | `parent_id IN (60)` + `created_at >= 14일` | `created_at DESC` | 60 × 365 = 21,900행/년 |
| `safety_alerts` | `elder_id IN (60)` + `acknowledged_at IS NULL` | — | 미확인 알림 누적 |

**누락 인덱스 3개 → `docs/migration-v2-performance-indexes.sql` 신규 생성**

1. `idx_social_scores_parent_week` — `(parent_id, week_start DESC)` 복합 인덱스
   - 현재: 전체 social_scores 스캔 후 parent_id 필터 + 정렬
   - 인덱스 후: parent_id로 직접 접근, week_start 이미 정렬됨 → JS에서 최신 2개 추출 O(1)

2. `idx_care_call_attempts_parent_created` — `(parent_id, created_at DESC)` 복합 인덱스
   - 현재: 14일 날짜 범위 전체 스캔
   - 인덱스 후: parent_id 범위 + created_at 필터를 인덱스 단에서 처리

3. `idx_safety_alerts_unacked` — `(elder_id)` WHERE `acknowledged_at IS NULL` 부분 인덱스
   - 현재: safety_alerts 전체 스캔 + IS NULL 필터
   - 인덱스 후: 미확인 알림만 인덱싱 → 확인된 알림은 인덱스 크기에서 제외, 쿼리 대상도 최소화

### 문제와 해결 과정

- 실측(60명 데이터) 불가 → 구조적 분석으로 대체
- `social_scores`와 `care_call_attempts`는 지금 당장은 빠르지만 운영 3~6개월 후 병목이 될 지점을 미리 차단
- `parent_profiles`는 60행 수준에서 정렬 인덱스가 불필요 — 작성 않음 (YAGNI)

### 기술적 의사결정

- **복합 인덱스 vs 단일 인덱스**: `IN (parent_id)` + `ORDER BY week_start`를 복합 인덱스 하나로 커버. PostgreSQL의 Index Only Scan이 가능해져 테이블 힙 접근을 줄인다.
- **부분 인덱스(partial index)**: `safety_alerts`는 `acknowledged_at IS NULL`인 행만 KPI에서 필요. 확인된 알림은 인덱스에서 제외해 크기 최소화 + 쿼리 최적화 동시 달성.
- **`Promise.all` 유지**: 4개 쿼리가 독립적이고 각각 인덱스로 최적화되면 병렬 실행이 최선. N+1이 없으므로 현재 구조 그대로 유지.

### 테스트 및 검증

- 실측 불가 (60명 더미 데이터 없음)
- 구조 분석 완료: 인덱스가 없는 상태에서 예상 병목 지점과 개선 방향 명시
- SQL 검증 쿼리를 파일 하단 주석으로 포함 (`pg_indexes` 조회)
- **실데이터 확보 후 할 일**: Supabase SQL Editor에서 `EXPLAIN ANALYZE`로 실제 실행 계획 확인

- `docs/migration-v2-performance-indexes.sql`: 성능 인덱스 SQL 신규 생성 (Supabase에서 직접 실행 필요)
