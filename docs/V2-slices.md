## 2. 작업 단위 규칙
- 작업은 Day > Slice 로 쪼개서 진행한다.
- 슬라이스 1개 = 커밋 1개 = 되돌릴 수 있는 최소 단위.
- 슬라이스 시작 시 "▶ Day N / Slice M — [이름] 시작" 을 먼저 출력한다.
- 슬라이스 종료 시 아래를 수행한다.
    · 변경 파일 목록 보고
    · PRD 수용 기준 체크 결과 보고 (충족/미충족)
    · docs/V2-progress.md 갱신 (체크박스 + 커밋 해시 + 현재 위치 + 다음 작업)
    · 다음 슬라이스 예고
- 수용 기준을 하나라도 충족하지 못하면 커밋하지 말고 원인을 보고한다.
- 커밋 시 CLAUDE.md 의 개발일지 규칙(docs/work-log/)을 반드시 따른다.
- 개발일지에는 "막혔던 지점과 그 원인"을 반드시 남긴다. (전자책 원고로 재사용됨)

## 3. 절대 규칙
1. 어르신은 아무것도 하지 않는다. 어르신 측 화면·버튼·설치를 전제한 기능은 거부한다.
2. 복지사에게 입력을 더 시키지 않는다. "또 하나의 입력 화면"이 되면 실패다.
3. PRD에 없는 기능은 만들지 않는다. 필요해 보이면 docs/BACKLOG.md 에 적기만 한다.
4. 저장소·앱을 분리하지 않는다. 개인용/기관용은 role 분기로만 구분한다.
5. 기존 화면을 다시 디자인하지 않는다. 신규 화면은 docs/design-system.md 를 따른다.
6. 한 슬라이스에서 3회 시도해도 막히면 멈추고 보고한다. 혼자 우회하지 마라.

## 5. 컨텍스트 복구 프로토콜
오너가 "V2 복구" 라고 말하면 아래를 순서대로 수행한다.
  1) CLAUDE.md → docs/PRD-v2-org-mvp.md → docs/V2-slices.md → docs/V2-progress.md 를 읽는다
  2) git log 로 최근 커밋을 확인해 progress 파일과 실제 상태가 일치하는지 대조한다
  3) 불일치가 있으면 실제 커밋 기준으로 progress 파일을 정정한다
  4) "현재 위치 / 다음 작업 / 대기 중인 승인" 3줄을 보고한다
  5) 승인 대기가 없으면 다음 슬라이스를 이어서 진행한다
※ progress 파일이 최신이 아니면 복구가 불가능하다. 슬라이스마다 반드시 갱신할 것.

### Day 34 — F1 기관 테넌시 (최우선)
목적: 지금 RLS가 owner_user_id = auth.uid() 단일 소유자라 기관에 팔 수 없다.

- S1. 영향도 조사 (읽기 전용, 코드 수정 금지)
      · 영향받는 테이블 전체 목록
      · 현재 RLS 정책 전문
      · owner_user_id 참조 코드 위치 전부
- S2. 🛑 마이그레이션 계획 제시 후 승인 대기
      organizations / org_members / parent_profiles(org_id, assigned_user_id)
      + RLS 정책 초안. 승인 없이 SQL 실행 금지.
- S3. 마이그레이션 적용 (org_id IS NULL 경로는 기존과 100% 동일 동작 보장)
- S4. RLS 정책 재작성
      · org_id IS NULL → owner_user_id = auth.uid()
      · org_id NOT NULL → auth.uid() ∈ org_members
      · role='field_worker' → assigned_user_id = auth.uid() 인 어르신만
- S5. 서버 코드 org 스코프 반영 (caseworker-queries.ts 등)
- S6. 멤버 초대 플로우 (센터장 이메일 초대 → 가입 시 org_members 자동 편입)
- S7. 회귀 테스트(기존 개인 데이터 무손상) + RLS 침투 테스트
      ※ 타 기관 데이터가 한 번이라도 조회되면 사업이 끝난다. 이 테스트는 CI에 고정한다.
