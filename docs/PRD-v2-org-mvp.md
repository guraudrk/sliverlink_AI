## 1. 한 문장 정의

> **SilverLink V2는 "가족이 쓰는 돌봄 앱"이 아니라, "돌봄 기관이 통화 기록 업무를 없애기 위해 구독하는 업무 도구"다.**

1차 MVP는 *어르신 1명 ↔ 자녀 1명*을 가정하고 만들어졌다.
V2는 *기관 1곳 ↔ 복지사 N명 ↔ 어르신 수십~수백 명*을 가정한다.
**이 전제 변경이 이 문서의 전부이며, 나머지는 그 결과다.**

---

## 2. 제품 제1원칙 (위반 시 스펙 거부)

1. **어르신은 아무것도 하지 않는다.** 설치·터치·화면 확인을 요구하는 기능은 설계 단계에서 거부한다.
2. **복지사에게 입력을 더 시키지 않는다.** 그들은 이미 정부 지정 업무 시스템에 기록을 입력하고 있다.
   우리의 가치는 **입력을 없애고, 그 시스템에 붙여넣을 결과물을 대신 만들어 주는 것**이다.
   → "또 하나의 입력 화면"이 되는 순간 계약은 실패한다.
3. **로보콜 영역에 들어가지 않는다.** 클로바 케어콜은 *AI가 어르신에게 전화를 건다*.
   우리는 *사람이 건 진짜 통화를 분석한다*. 이 경계를 넘으면 이길 수 없는 싸움이 된다.
4. **저장소·앱을 분리하지 않는다.** 개인용/기관용은 `role` 분기로만 구분한다.
   (Play Store 심사 3회 거절 이력. 심사 대상을 2개로 늘리는 것은 자해다.)

## 3. 고객 정의 — 누가 돈을 내는가

### 3.1 1순위 타겟 (민간, 의사결정 빠름)

| 항목 | 내용 |
|---|---|
| 고객 | 방문요양센터 · 주간보호센터 |
| 결정권자 | **센터장 1명** |
| 규모 | 어르신 20~80명 / 요양보호사 다수 |
| 페인 | 어르신 상태 기록·보고 의무, 이직률 높은 인력의 인수인계 |
| 계약까지 | **2~6주** |

### 3.2 2순위 타겟 (공공 위탁, 규모 큼·느림)

| 항목 | 내용 |
|---|---|
| 고객 | **노인맞춤돌봄서비스 수행기관** (지자체 위탁, 전국 수백 개소) |
| 구성 | 전담사회복지사 + 생활지원사 |
| 업무 | 생활지원사가 담당 어르신 수십 명에게 **매일 안부 전화 + 기록 입력** |
| 페인 | 통화는 이미 하고 있는데 **기록·보고가 별도 노동**. 사회복지사 시간의 50~65%가 행정 |
| 계약까지 | **3~6개월** (예산 주기·개인정보 검토) |

> **영업 순서: 민간 3곳으로 레퍼런스를 만든 뒤 공공으로 올라간다.** 공공부터 치면 6개월간 매출 0이다.

### 3.3 개인(family) 트랙의 새 역할

**버리지 않되, 매출 트랙에서 제외한다.** 개인용은 **무료 티어 + 유입 경로**로만 유지한다.
개인 사용자가 늘어나는 것은 KPI가 아니다. 개인용 신규 기능 개발은 **0**이다.

## 7. 기능 명세

### F1. 기관 테넌시 — **최우선. 이것 없이는 아무것도 팔 수 없다**

**문제**: 현재 모든 RLS가 `owner_user_id = auth.uid()`. 어르신은 만든 사람만 본다.
기관에서는 생활지원사 A가 담당한 어르신을 전담사회복지사 B가 반드시 봐야 한다.

**데이터 모델 변경**

```
organizations
  id, name, type('private_care'|'public_program'), created_at

org_members
  id, org_id, user_id, role('admin'|'social_worker'|'field_worker'), created_at
  -- admin: 센터장 / social_worker: 전담사회복지사 / field_worker: 생활지원사·요양보호사

parent_profiles (기존 테이블 확장)
  + org_id           uuid null      -- null이면 기존 개인(family) 데이터
  + assigned_user_id uuid null      -- 담당 복지사

-- RLS 정책 (핵심)
-- org_id IS NULL      → owner_user_id = auth.uid()            (기존 개인 사용자 그대로 동작)
-- org_id IS NOT NULL  → auth.uid() ∈ org_members(org_id)      (같은 기관이면 조회 가능)
--   단 role='field_worker' → assigned_user_id = auth.uid() 인 어르신만
```

**수용 기준**

- [ ] 기존 개인 사용자 데이터가 **하나도 깨지지 않는다** (`org_id IS NULL` 경로 회귀 테스트 통과)
- [ ] 생활지원사는 본인 담당 어르신만 조회된다
- [ ] 전담사회복지사·센터장은 기관 전체 어르신이 조회된다
- [ ] 다른 기관의 데이터는 **어떤 경로로도** 조회되지 않는다 (RLS 침투 테스트 필수)
- [ ] 초대 플로우: 센터장이 이메일로 멤버 초대 → 가입 시 자동으로 `org_members` 편입

> ⚠️ **다른 기관 데이터가 한 번이라도 보이면 그 순간 이 사업은 끝난다.** 이 항목은 테스트 없이 머지하지 않는다.

### F2. 기관 통합 대시보드

기존 `caseworker/page.tsx`를 **기관 스코프로 확장**한다. 새로 만들지 않는다.

**화면 요구**

- 상단 KPI: 담당 어르신 수 / 🔴 즉시 확인 / 🟠 추세 악화 / 이번 주 미통화
- **위험도 정렬이 기본값** (`getRiskWeight` 재사용). 이름순 정렬은 부차적
- 각 카드에 **플래그 사유 문자열을 그대로 노출** (`risk-flags.ts`의 `reason`)
  → 근거를 숨기지 않는 것이 복지사 신뢰의 핵심이다
- 담당자 필터 (전담사회복지사·센터장 전용)
- 어르신 60명 기준 **초기 로딩 2초 이내** (현재 4배치 쿼리 구조 유지, 필요 시 인덱스 추가)

**수용 기준**

- [ ] 어르신 60명 시드로 2초 이내 렌더
- [ ] 위험 플래그 사유가 화면에 문자열로 보인다
- [ ] 역할별로 보이는 범위가 F1 정책과 정확히 일치한다

### F3. AI 배치 리포트 — 수동 1인분 → 자동 N인분

기존 `/api/ai/care-report`는 **1명·수동·스트리밍**이다. 배치 경로를 **별도로** 만든다.
(기존 라우트는 화면 미리보기용으로 유지)

```
POST /api/reports/batch
  body: { orgId, periodStart, periodEnd, elderIds? }
  → 어르신별 리포트 생성 → reports 테이블 저장 → { reportSetId }

reports
  id, org_id, parent_id, period_start, period_end,
  summary_md, paste_text, risk_level, generated_at, model
```

**리포트 내용 (복지사가 실제로 쓰는 것만)**

1. 이번 주 통화 횟수 / 응답률
2. **상태 변화 요약 3줄** — 지난주 대비
3. 위험 플래그와 **그 근거 문장**
4. 통화에서 나온 특이사항 (수면·식사·통증·외출·정서 언급)
5. **권장 조치 1개** — 여러 개 주면 아무것도 안 한다

**수용 기준**

- [ ] 어르신 60명 배치가 **5분 이내** 완료 (Vercel 함수 제한 고려해 청크 분할·재개 가능)
- [ ] 실패한 건은 개별 재시도 가능, 전체가 실패하지 않는다
- [ ] 데이터가 부족한 어르신은 **환각 대신 "데이터 부족"을 명시**한다 ← 신뢰의 문제

### F4. 정해진 시각 자동 발송

```
report_schedules
  id, org_id, cron_expr, recipients(text[]), enabled, last_run_at

POST /api/cron/weekly-reports   (Bearer CRON_SECRET — 기존 패턴 재사용)
  → 대상 org 조회 → F3 배치 실행 → 이메일 발송 → 결과 기록
```

- 기본값: **매주 월요일 08:00 KST** (주간 업무 시작 직전)
- 수신자: 전담사회복지사·센터장 이메일 (복수)
- 메일 본문: 기관 전체 요약 + 🔴 위험 어르신 목록 / 첨부: 전체 리포트 (CSV + PDF)
- 발송 실패 시 재시도 후 관리자 알림

> **비용 주의**: Vercel Hobby 플랜은 크론 실행 빈도에 제한이 있다. 주 1회 스케줄로 충분하며,
> 제한에 걸리면 외부 스케줄러(GitHub Actions cron)로 우회한다. **고정비 월 30만원을 넘기지 않는다.**

**수용 기준**

- [ ] 지정 시각에 자동 발송된다
- [ ] 발송 이력이 조회된다 (기관에 "지난주 것 다시 주세요"를 답할 수 있어야 함)
- [ ] `CRON_SECRET` 없이 호출되지 않는다

### F5. 붙여넣기 가능한 출력 포맷 — **이게 구매 이유다**

복지사는 우리 화면이 아니라 **자기 업무 시스템**에 기록해야 한다.
따라서 최종 산출물은 *예쁜 대시보드*가 아니라 **복사 가능한 텍스트 블록**이다.

- 어르신 카드마다 **[기록 복사]** 버튼 → 클립보드에 즉시 복사
- 복사 형식 (기본 템플릿, 기관별 커스터마이즈 가능):

```
[2026-07-27 ~ 2026-08-02] 홍길동 어르신
· 통화 5회 중 4회 응답 (응답률 80%)
· 특이사항: 수면 곤란 2회 언급, 무릎 통증 호소 1회
· 상태: 전주 대비 소폭 하락 (58점 → 51점)
· 권장: 방문 시 수면 상태 확인 필요
```

- CSV 일괄 다운로드 (기관 보고용)
- **템플릿 문구는 코드 하드코딩 금지 — DB에서 기관별로 수정 가능해야 한다**

**수용 기준**

- [ ] 복사 버튼 1회로 위 형식이 클립보드에 들어간다
- [ ] 기관이 템플릿 문구를 스스로 수정할 수 있다
- [ ] CSV가 엑셀에서 한글 깨짐 없이 열린다 (UTF-8 BOM)

### F6. 영업 데모 모드 — **없으면 영업을 시작할 수 없다**

계약 전에는 고객 데이터가 0이다. **빈 대시보드로는 아무것도 팔 수 없다.**

- `POST /api/demo/seed-org` → 가상 기관 1곳 + 어르신 30명 + 4주치 통화·점수·알림 생성
- 데모 계정으로 로그인하면 **위험 플래그가 이미 켜져 있는 상태**로 보인다
- 시연 시간 **3분 이내**에 "문제 발견 → 리포트 → 복사" 전체 플로우가 돌아야 한다
- 기존 `/api/recordings/seed` 확장으로 구현

**수용 기준**

- [ ] 명령 1회로 데모 기관이 생성된다
- [ ] 데모 데이터가 실 데이터와 **절대** 섞이지 않는다 (`organizations.is_demo`)
- [ ] 노트북 하나로 오프라인 시연 가능 (네트워크 불안정 대비 캐시)

### F7. 개인정보 처리 기본 세트 — 기관 계약의 실제 관문

기능이 아무리 좋아도 이게 없으면 **계약서 단계에서 멈춘다.**

- [ ] 녹음 원본은 **분석 후 즉시 파기**가 기본값. 보관은 기관 옵트인 + 보관 기간 설정
- [ ] 어르신 **본인 동의 획득 절차**를 제품 안에 명시 (동의 일자·방법 기록)
- [ ] 저장 데이터 암호화 / 접근 로그 (누가 언제 어떤 어르신 데이터를 봤는가)
- [ ] 기관 관리자용 **데이터 삭제 요청** 기능
- [ ] `docs/privacy-for-orgs.md` — 기관 검토용 1장 요약 (계약 실무자가 요구한다)

## 8. AI 에이전트 자동화 계층

> 사용자 방향: 헤르메스 에이전트 / OpenClaw 등을 활용해 리포트 생성·발송을 자동화.

**단, 이 PRD에서의 원칙은 하나다.**

> **핵심 경로(리포트 생성·발송)는 코드로 구현한다. 에이전트는 그 위에 얹는다.**

이유: 고객에게 파는 기능이 에이전트 프레임워크에 의존하면, 프레임워크가 흔들릴 때 **매출이 흔들린다**.
F3·F4는 순수 API + cron으로 확정하고, 에이전트는 아래처럼 **주변부**에 배치한다.

| 계층 | 담당 | 구현 |
|---|---|---|
| 리포트 생성·발송 | **코드** (F3·F4) | 결정적·재시도 가능·테스트 가능 |
| 리드 수집·제안 메일 초안 | 에이전트 | 실패해도 매출에 영향 없음 |
| 주간 운영 요약 (오너용) | 에이전트 | 내부용 |
| 고객 문의 1차 분류 | 에이전트 | 고객 5곳 이후 |

**리포트 품질 검증만은 LLM 2단계로 한다**: 생성 → 별도 프롬프트로 사실성 검토(수치 일치·환각 여부) → 실패 시 "데이터 부족"으로 대체.

## 9. 가격 (파일럿 계약용 초안)

| 플랜 | 대상 | 가격 |
|---|---|---|
| 파일럿 | 신규 기관 | **3개월 무료** (조건: 4주 뒤 절감 시간 응답) |
| 기본 | 어르신 ~30명 | **월 15만원** |
| 표준 | 어르신 ~100명 | **월 30만원** |
| 기관 확장 | 100명 초과 | 어르신당 **월 3,000원** |

- 인원당 과금이 기관 입장에서 **예산 품의를 쓰기 쉽다**. "1인당 3천 원"은 반박이 어려운 숫자다.
- **월 300만원 = 표준 플랜 10곳.** 20~30곳까지 안 가도 된다.
- 파일럿 무료의 대가는 돈이 아니라 **before/after 데이터와 추천서**다. 계약서에 명시한다.

## 13. 열어둔 결정 (파일럿 미팅에서 확정)

1. 리포트 주기 — 주 1회 / 격주 / 월 1회 중 무엇을 실제로 원하는가

4. 녹음 보관 — 기관이 보관을 원하는가, 파기를 원하는가 (예상: 파기 선호)
