# SilverLink 코딩 가이드라인

Andrej Karpathy 스타일 LLM 코딩 실수 감소 규칙을 이 프로젝트에 맞게 정리한 문서.
원본 출처: https://github.com/datajuny/andrej-karpathy-skills/blob/main/CLAUDE.md

**적용 범위:** Day 37 이후 모든 구현. Day 34~36 소급 수정 안 함.
**편향:** 속도보다 신중함. 사소한 작업은 판단으로 조정한다.

---

## §1 State Assumptions, Then Proceed — 가정을 말하고 진행한다

구현 전에 가정을 한 줄로 말하고 바로 시작한다.

- 해석이 여럿이면 가장 그럴듯한 것을 골라 어떤 것을 골랐는지 말한다.
- 더 단순한 방법이 있으면 작업 중에 말한다. 질문으로 막지 않는다.
- 답이 **무엇을 만들지**를 바꾸고, 잘못 선택하면 되돌리기 어려울 때만 질문한다.

가정은 말하면 몇 초 안에 수정된다. 질문은 왕복 비용을 쓰고 일을 오너에게 돌려준다.
한 작업에서 두 번째 질문을 하려 한다면, 방법이 틀린 것이다.

---

## §2 Simplicity First — 최소 코드로 문제를 해결한다

요청한 것만 만든다. 추측으로 만드는 것은 없다.

- 요청하지 않은 기능 없음.
- 단일 용도 코드에 추상화 없음.
- 요청하지 않은 "유연성"이나 "설정 가능성" 없음.
- 불가능한 시나리오에 대한 오류 처리 없음.
- 200줄로 짰는데 50줄이 가능하면 다시 짠다.

스스로에게 묻는다: "시니어 엔지니어가 과도하게 복잡하다고 할까?" 그렇다면 단순화한다.

### ⚠️ V2 예외 — 오너가 명시적으로 요청한 설정값 4개

아래 4개는 **단순성 규칙의 예외**다. 이것들은 기관 미팅 전에 개발하므로
추측으로 고정(하드코딩)하면 나중에 전부 뜯어야 한다.

| 항목 | 저장 위치 |
|---|---|
| 리포트 주기 | `report_schedules.cron_expr` 컬럼 |
| 붙여넣기 템플릿 | `paste_templates` DB + 기관 관리자 편집 UI |
| 수신 채널 | 채널 인터페이스 추상화 + 이메일 구현체 1개 |
| 녹음 보관 | 기본 파기 + 기관 옵트인 토글 |

이 4개 외의 설정화·추상화는 원칙대로 금지한다.

## §3 Surgical Changes — 꼭 바꿔야 할 것만 바꾼다

기존 코드를 편집할 때:
- 인접 코드·주석·포맷을 "개선"하지 않는다.
- 망가지지 않은 것은 리팩터링하지 않는다.
- 자신의 스타일이 달라도 기존 스타일을 맞춘다.
- 무관한 죽은 코드를 발견하면 언급만 하고 삭제하지 않는다.

자신의 변경이 고아를 만들었을 때:
- 자신의 변경이 만든 미사용 import·변수·함수만 제거한다.
- 기존에 있던 죽은 코드는 요청 없으면 건드리지 않는다.

**판단 기준:** 변경된 모든 줄이 오너의 요청까지 직접 추적 가능해야 한다.

이것은 CLAUDE.md의 기능 동결 규칙과 같은 방향이다. 더 강하게 적용한다.

---

## §4 Plan Before Code — 복잡한 작업은 먼저 구조를 잡는다

슬라이스 하나가 파일 3개 이상이거나 DB 스키마를 건드리면:
- 변경할 파일 목록과 각 파일의 역할을 먼저 나열한다.
- 의존 순서(migration → service → route → UI)를 확인한다.
- PRD 수용 기준을 먼저 읽고, 기준을 충족하지 못하면 커밋하지 않는다.

V2에서 계획 문서는 `docs/PRD-v2-org-mvp.md`, 실행 체크리스트는 `docs/V2-slices.md`다.
새 계획 파일을 만들지 않는다.

---

## §5 Teach One Thing On The Way Out — 끝낼 때 한 가지를 가르친다

작업이 끝나면:
- 이번에 실제로 중요했던 개념·트레이드오프·함정을 하나 짚는다.
- 코드가 보여주지 않는 것을 설명한다: 왜 다른 방법을 안 썼는지, 어떤 기본값에 의존했는지, 규모에서 무엇이 먼저 깨지는지.
- 제목이 필요할 만큼 길어지면 너무 긴 것이다. diff를 다시 설명하면 삭제한다.
- 변경이 사소하거나 오너가 가르쳐준 내용이면 생략한다.

에이전트가 코드만 납품하면 오너는 유지보수할 수 없게 된다.

---

## §6 Don't Break the Working State — 작동하는 것을 건드리지 않는다

현재 작동 중인 기능을 건드릴 때는:
- 변경 전 `git diff`로 범위를 확인한다.
- 테스트가 있으면 변경 전후에 실행한다.
- 작동하던 것이 깨지면 즉시 말한다. 계속 진행하지 않는다.
- 버그를 발견했더라도 현재 요청 범위 밖이면 언급만 하고 고치지 않는다.

작업 도중 예상치 못한 파일·브랜치·설정을 발견하면 삭제·덮어쓰기 전에 오너에게 확인한다.

---

## §7 Map Outputs to Existing Files — 새 파일을 만들지 않는다

새 문서(checklist.md, context-notes.md 등)를 만들지 않는다.
이미 같은 역할의 파일이 있다.

| 역할 | 기존 파일 |
|---|---|
| Plan | `docs/PRD-v2-org-mvp.md` |
| 체크리스트 | `docs/V2-slices.md` + `docs/V2-progress.md` 체크박스 |
| 결정 기록 | `docs/V2-progress.md` "결정 기록" 섹션 |
| 작업 일지 | `docs/work-log/YYYY-MM-DD.md` |
| 백로그 | `docs/BACKLOG.md` |

관리 지점을 늘리지 않는다. 새 파일이 필요하다면 오너에게 먼저 확인한다.

---

## §8 Test to Completion — 검증 없이 완료라고 말하지 않는다

슬라이스 종료 시 아래를 순서대로 실행하고 결과를 보고한다.

1. `npx tsc --noEmit` — 타입 에러 없음 확인
2. 프로젝트 정의 테스트 실행
   - `playwright.config.ts` 존재 확인 → 해당 스크립트 실행
   - 그 외 `package.json` scripts의 `test` 명령
3. 위 둘로 검증 불가한 항목은 "무엇을 검증하지 못했는가"를 명시적으로 보고

"done", "완료", "끝"은 구체적인 검증 결과가 뒷받침할 때만 사용한다.
오너가 신호를 보내기 **전에** 선제적으로 실행한다.

이것이 LLM이 가장 많이 건너뛰는 단계다. 협상 불가로 취급한다.

---

## §9 Stay in Scope — 범위를 벗어나지 않는다

기능 추가 요청이 들어왔을 때:
- 유료(또는 파일럿) 기관이 직접 요구한 기능인가? → 만든다.
- 아니면 → `docs/BACKLOG.md`에 적고 만들지 않는다.

범위 밖이라는 신호:
- "있으면 좋을 것 같아서"
- "어차피 나중에 필요할 것 같아서"
- "이 기회에 같이 개선하면 좋겠다"

리팩터링·기술 스택 교체는 매출에 직접 기여하지 않으면 후순위다.
이 프로젝트의 최대 실패 위험은 버그가 아니라 계속 기능을 더 만드는 것이다.

---

## §10 Read Errors, Don't Guess — 에러를 읽는다. 추측하지 않는다

**실패하면:**
1. 전체 에러 메시지와 스택 트레이스를 먼저 읽는다.
2. 로그를 실제로 확인한다. 추측한 내용이 아니라 출력된 내용을 본다.
3. 원인을 확정하기 전에 "흔한 해결책"을 적용하지 않는다.
4. 불명확하면 로그를 추가해 상태를 확인한 뒤 고친다.

**실제 사례 — Day 36 `auth.uid()` NULL 오진단:**

`parent_profiles` INSERT 실패를 `auth.uid()` NULL로 잘못 진단했다.
결과: 정책 단순화 → 미들웨어 추가 → SECURITY DEFINER 우회 — 세 번 추측, 세 번 빗나갔다.

실제 원인은 `organizations` 테이블에 INSERT 정책이 없어서 org 생성이 먼저 실패한 것이었다.
RLS 에러 메시지는 원인이 아니라 결과를 보고한다. 체인의 첫 번째 실패 지점을 찾아야 한다.

**판단 기준:** "이 가설을 뒷받침하는 실제 출력이 있는가?" — 없으면 로그를 추가한다.

---

**이 가이드라인이 작동하고 있다면:** diff에서 불필요한 변경이 줄고, 과도한 추상화로 인한 재작성이 줄고, 가정이 늦게 터지지 않고 초반에 수정된다.
